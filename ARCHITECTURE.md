# Architecture

## Repository assessment

The repository started empty: it contained only the supplied product specification (`message (1).txt`). There was no package manifest, application code, database schema, deployment config, or existing design system to preserve. The application is therefore being established as a greenfield Next.js project.

## Product and delivery decisions

- Build the P0 workflow first: authentication, onboarding, dashboard, exercise catalog, workout logging, completion, history, local persistence, and synchronization.
- Treat a workout as relational data. Sets are rows, not an opaque JSON document. Local drafts may be represented as a versioned local record for fast offline writes, then synchronized into normalized server tables.
- Keep workout logging usable without an account connection. Cloud sync is an enhancement for persistence across devices, not a runtime prerequisite for an active workout.
- Use Supabase Auth and PostgreSQL with RLS. Every user-owned row is scoped to `auth.uid()`; system exercise rows are readable by all authenticated users.
- Keep deterministic calculations (volume, estimated 1RM, PRs, progression) in typed domain modules, separate from UI and persistence.
- Keep the server/client boundary explicit: server components load account-backed data; client components own interactive workout state and local-first interactions.
- Avoid an AI or billing dependency in the core workflow. Feature gates can be added when paid or AI features are implemented.

## Proposed architecture

Next.js App Router with TypeScript and Tailwind. Application routes live under route groups in `src/app`; reusable primitives are in `src/components/ui`; product components are grouped by feature. Feature modules own schemas, domain functions, and data access boundaries. Zustand is reserved for transient cross-component client state; active workout state is persisted through an IndexedDB repository. Supabase is accessed through isolated browser/server clients and route handlers or server actions, never directly from arbitrary components.

## Database schema

The first migration establishes the P0 relational base and leaves P1/P2 tables for their implementation phases. UUID primary keys are generated by PostgreSQL. `user_id` ownership and RLS are mandatory for private data.

### P0 entities

- `profiles`: `id` references `auth.users`, display name, experience, optional demographic fields, goals, preferences, timestamps.
- `muscles`: normalized system catalog (`id`, unique `slug`, display name, region).
- `exercises`: system or user-owned catalog entries with name, slug, aliases, instructions, primary muscle, movement pattern, equipment, difficulty, rep range, rest seconds, archive state, timestamps.
- `exercise_muscles`: exercise-to-muscle mapping and analytics contribution weight (a configurable model, not a physiological measurement).
- `workouts`: owner, name, timestamps, duration, status, notes, optional template/program references, timestamps.
- `workout_exercises`: workout/exercise relation, ordering, name snapshot, notes, rest seconds, optional superset group.
- `sets`: normalized set rows with weight, reps, RPE/RIR, set type and completion/technique flags.
- `exercise_favorites`: user and exercise relation.

P1 adds programs, program weeks/days, bodyweight, measurements, and PR snapshots. P2 adds photos and readiness/plateau observations. Avoid adding tables before a feature has a real workflow.

## Component architecture

Layout components provide responsive desktop sidebar and mobile navigation. Feature screens compose focused components. The active workout decomposes into `WorkoutHeader`, `WorkoutStats`, `ExerciseList`, `ExerciseCard`, `PreviousPerformance`, `SetList`, `SetRow`, `RestTimer`, and `WorkoutFooter`. `SetRow` owns presentation and input events only; domain calculations and persistence remain in feature modules. Destructive actions use a shared confirmation primitive. UI primitives are centralized and extended, not reimplemented per feature.

## State architecture

- Server state: Supabase through server-side repositories and authenticated route handlers/server actions.
- Active workout: typed workout aggregate in an IndexedDB-backed repository; Zustand holds the currently hydrated in-memory draft and UI-only state.
- Preferences and lightweight cache: versioned local storage only when the data is small and non-sensitive.
- Mutations: validate with Zod, write locally first for active logging, enqueue idempotent sync operations, then reconcile server acknowledgements.
- Do not use a global store as a substitute for the relational data model.

## Offline and synchronization strategy

The app shell and versioned static assets are cached by a service worker. Workout edits are persisted to IndexedDB before the UI acknowledges them. An outbox records operations with stable client-generated IDs and `updated_at`/revision metadata. Sync runs on reconnect, app focus, and explicit retry. Server writes are idempotent; the server validates ownership and data constraints. Conflicts are resolved per entity using revision/version metadata: active drafts favor the newest local edit for the same client, while completed server history is not silently overwritten. Failed operations remain queued and visible as a recoverable sync state. The active draft survives refresh and temporary connection loss.

## Security and validation

Supabase RLS policies enforce profile, workout, exercise, and set ownership. System exercise data is read-only to users; custom exercises require `created_by = auth.uid()`. Server-side handlers validate input and session before database writes. Never expose service-role credentials to the client. Enforce nonnegative weight/reps and bounded RPE/RIR in both application validation and database constraints where appropriate.

## Major dependencies

Next.js, React, TypeScript, Tailwind CSS, shadcn/ui primitives, Lucide, Zustand, React Hook Form, Zod, date-fns, Recharts, and Supabase JS/SSR. Add dependencies only alongside a concrete feature; service worker and IndexedDB support should use browser APIs or a small maintained library after compatibility is confirmed.

## Implementation phases

1. Foundation: Next.js, theme/layout, navigation, Supabase clients, initial schema/RLS, local persistence base, and environment documentation.
2. Workout engine: exercise catalog/search, workout creation, set rows, rest timer, completion, and history.
3. Analytics: PRs, estimated 1RM, volume, muscle contribution, exercise history, and trends.
4. Programs: builder, schedule, execution, progression rules.
5. Physique: bodyweight, measurements, photos.
6. Intelligent features: plateau/readiness heuristics and substitutions.
7. AI features, only after reliable P0 data.
8. Social features, only after core workflows.
9. Polish: accessibility, performance, PWA/offline/sync and security verification.

## Current implementation status

The repository now has the Next.js foundation and a local-first workout vertical slice: email/password signup and login, profile onboarding, a built-in 40-movement catalog with deterministic name/alias/muscle/equipment search, IndexedDB-backed active/completed sessions, set entry and completion, automatic adjustable rest countdown (including restore after refresh), session notes, calculated totals, previous-session performance, dashboard summaries, and completed workout history. The initial Supabase schema and RLS policies plus a system exercise/muscle seed are present. A production service worker caches the app shell, navigation responses, static assets, and Next.js RSC navigation responses; workout draft data itself remains in IndexedDB.

Authentication/profile persistence uses Supabase when environment variables are configured. Completed workouts sync as idempotent upserts when online after sign-in; failed writes remain in IndexedDB and retry on reconnect or app focus. Active drafts stay local until completion. Sync conflict resolution, editing synced history, multi-device behavior, and an automated browser flow remain to be built and verified. The app catalog currently uses a typed bundled copy of the system exercise seed so the core picker works before Supabase environment setup; keep those two catalogs aligned until exercise reads move to a repository.

## Analytics methodology

Volume is `weight × reps` for completed working sets (with explicit product rules for bodyweight and assisted movements). Muscle volume is set volume multiplied by the configured exercise-muscle contribution weights. Frequency counts sessions with a relevant exposure. These are consistent product analytics conventions, not objective measurements of physiological stimulus.
